# Zstar v1

**Status:** working draft.

## Terminology and conformance

A **conformant archive** satisfies all layout, frame, tar, manifest, pointer,
and cross-field rules in this document, even if referenced external objects are
unavailable. A **complete external closure** supplies valid, complete raw
objects for every external extent. A valid archive may contain entries that a
host filesystem cannot represent.

Implementations declare which conformance classes they support:

| Class | Minimum behavior |
| --- | --- |
| Portable writer | Emit a conformant archive with only archive-backed file extents. |
| Thin writer | Emit a conformant archive; declare `external-content` exactly when external extents occur. |
| Metadata reader / full metadata validator | Authenticate all decoded metadata, validate the complete deterministic CBOR sequence, schema, namespace and required features. |
| Selective reader | Perform metadata-reader checks and validate each selected complete source and extent before returning its requested bytes. |
| Full archive validator | Perform full metadata validation and validate every physical frame, tar member, payload mapping, pointer and end record. |
| External resolver/reconstructor | Supply or consume complete bounded encoded objects; validate selected raw objects and reconstruct selections in order under the declared hash policy. |
| Filesystem capturer/restorer | Follow the normative [filesystem profile](#filesystem-capture-and-restoration-profile), in addition to the applicable writer/reader classes. |

Support for `external-content` includes interpreting external extents and
checking pointer agreement where required by the conformance class. Metadata
readers and full archive validators need not fetch external objects.
Portable-only implementations MAY reject `external-content`. Reconstructors
that support it MUST understand external addresses and decoded selections.
Unknown required features MUST be rejected before interpreting affected
entries.

An operation establishes only the checks it completes. Metadata validation and
selective reads do not establish full archive validity. Full archive validation
does not establish external availability, verified closure, or content
authenticity. Implementations MUST NOT claim checks they did not complete.
Rejection requirements apply to the structures and dependencies being
validated; selective readers need not inspect unrelated tar regions.

## Conventions

MUST, MUST NOT, SHOULD, and MAY have the BCP 14 meanings defined by RFC 2119
and RFC 8174. Wire definitions below are normative.

Offsets are zero-based; ranges are half-open. Sizes are measured in bytes. MiB
means 1048576 bytes. An archive or encoded source length MUST fit uint64.
Integers are unsigned 64-bit unless otherwise specified; `mtime_ns` is signed
64-bit nanoseconds since the Unix epoch. Booleans are not integers. All
arithmetic, rounding, and cumulative sums MUST be checked for overflow before
allocation, addressing, or slicing.

Byte positions use three coordinates:

| Coordinate | Origin and use |
| --- | --- |
| Encoded archive position | Byte zero of the archive; footer manifest offsets and integer extent sources use this coordinate. |
| Decoded tar position | Byte zero of the concatenated data-frame output; member headers, payloads and physical coverage use this coordinate. |
| Decoded source selection | Byte zero of one complete decoded frame or object; an extent's optional `offset` uses this coordinate. |

A file-read offset addresses the logical bytes formed by concatenating that
file's extent selections.

`roundUp(n, 512)` rounds `n` up to a multiple of 512; `roundUp(0, 512) = 0`.
The result MUST fit the address space and format limits.

## Layout

```text
[independent Zstandard data frames encoding one tar stream]
[metadata skippable frames containing segments of a compressed CBOR sequence]
[80-byte terminal skippable-frame footer]
```

Data frames occupy every byte before the metadata region. The metadata region
immediately precedes the footer, which ends the archive. No other skippable
frames or gaps are permitted.

### Zstandard frame requirements

Each data frame, compressed metadata segment, or external object contains
exactly one independently decodable Zstandard frame. Skippable frames,
concatenated frames, trailing bytes, and external dictionaries are forbidden
within a source range. Dictionary IDs MUST be absent or zero.

Encoded frames are limited to 17 MiB; decoded frames are limited to 16 MiB. The
window MUST NOT exceed 16 MiB, including for single-segment frames. Readers
MUST enforce these limits while decoding, before exceeding input, output, or
codec allocation budgets.

Data frames require checksums. Metadata and object checksums, and all
content-size fields, are optional; when present they MUST be valid. A declared
content size MUST equal the actual decoded length. Every frame MUST use
standard magic `0xFD2FB528` and RFC 8878 reserved-bit, block, and frame
encodings. The Frame_Header_Descriptor reserved bit (bit 3) MUST be zero.
Readers MUST ignore its unused bit (bit 4), as RFC 8878 specifies.

### Decoded tar stream

Tar members, PAX sequences, records, payloads, and padding MAY cross frame
boundaries. Several members MAY share a frame. Every data frame decodes to at
least one byte. The concatenated output MUST end with exactly two zero 512-byte
records and no trailing bytes. An empty archive has at least one data frame
encoding those 1024 zero bytes.

### Footer

The footer is exactly 80 bytes. Integer fields are unsigned little-endian;
offsets are absolute encoded archive positions.

| Offset | Bytes | Value |
| --- | --- | --- |
| 0 | 4 | Skippable magic `0x184D2A5F` |
| 4 | 4 | Payload length: 72 |
| 8 | 8 | ASCII `ZSTAR001` |
| 16 | 4 | Profile version: 1 |
| 20 | 4 | Reserved: zero |
| 24 | 8 | Start of the manifest region |
| 32 | 8 | Total encoded manifest region length, including every wrapper |
| 40 | 8 | Sum of decoded CBOR segment lengths |
| 48 | 32 | SHA-256 of concatenated decoded CBOR segment bytes, in physical order |

For archive length `N`, manifest offset `T`, and region length `L`, require `N
>= 80`, `T > 0`, `L > 8`, and `T + L = N - 80`, using checked arithmetic.
Reject incorrect magic, reserved values, versions, or digests, and any
inconsistent fields or bounds.

### Metadata region

Metadata wrappers exactly cover the manifest region. Each wrapper has an 8-byte
header followed immediately by one Zstandard payload. Its header fields are
little-endian uint32: magic `0x184D2A5E` and the encoded payload length.

Apply local aggregate budgets before fetching; format limits apply
independently to each segment. Decode and hash all segments in physical order,
checking the aggregate decoded length and SHA-256 against the footer before
using the manifest. The decoded sequence follows the [manifest
rules](#entry-oriented-manifest).

### Recognition and media type

Readers MUST validate the terminal footer and manifest before recognizing a
file as Zstar. A filename extension or media type is insufficient. V1 uses
`application/zstd`; generic `application/octet-stream` is acceptable. No Zstar
media type is registered. Ordinary Zstandard/tar tools can decode the tar
stream but do not interpret the index or resolve thin content.

## Tar profile

Use POSIX ustar with at most one nonempty local PAX header (`x`) immediately
before a member. Supported member types are regular file (`0` or NUL),
directory (`5`), and symlink (`2`). V1 excludes global PAX headers, hard links,
sparse files, devices, FIFOs, xattrs, and all other types. Writers MUST reject
unsupported input or explicitly convert it at the caller's request; readers
MUST reject unsupported encodings.

Numeric ustar fields contain octal digits with optional leading and trailing
ASCII spaces. A field may end with a NUL terminator or fill its width exactly;
only NUL or spaces may follow the digits. An empty numeric field or one
containing only spaces represents zero. Signs and GNU base-256 are forbidden.
Values MUST fit the applicable numeric range.

Header checksums sum unsigned bytes, treating the checksum field as spaces.
Owner and group display names are empty. Device major/minor fields MUST be zero
for every supported kind. Non-symlink member link fields and local PAX header
link fields MUST be empty. The `x` header has a valid checksum, its size is the
PAX payload length, and its name, mode, uid, gid and mtime are ignored. Header
and payload padding is zero.

Ustar path, prefix and link fields are UTF-8 with zero padding after any NUL
terminator. The path is `prefix + "/" + name` when the prefix is nonempty, and
`name` otherwise. PAX `path` replaces both prefix and name; PAX `linkpath`
replaces the ustar symlink target. Underlying fields require valid UTF-8 and
padding even when overridden. PAX supplies values that do not fit ustar. A
complete local PAX/member-header sequence is at most 1 MiB.

PAX permits only `path`, `linkpath`, `size`, `uid`, `gid`, and `mtime`. Reject
unknown or duplicate keys. Records use POSIX `<length> <key>=<value>` followed
by LF; the decimal length includes every byte of the record. Records MUST
consume the exact PAX payload length, excluding zero padding.

The [lexical grammar](#lexical-grammar) defines `pax-uint` and `pax-mtime`.
`size`, `uid` and `gid` accept one or more decimal digits, including leading
zeros, and MUST fit uint64. Signs, decimal points, and whitespace are
forbidden.

`mtime` permits an optional leading minus sign, one or more integer digits, and
an optional decimal point followed by one or more fractional digits. Leading
zeros and negative zero are accepted. A plus sign, `.5`, `1.`, exponents and
whitespace are rejected. Interpret `mtime` as exact decimal seconds since the
Unix epoch: its nanosecond value MUST be integral without rounding and fit
int64. Fractional digits after the ninth are accepted only when all are zero.
Ustar times are integral seconds. Overridden ustar fields still require valid
syntax, but need not equal their PAX values.

Apply PAX overrides before locating payloads or comparing with the manifest.
The effective path, kind, mode, uid, gid, mtime, and symlink target MUST match
the manifest entry. Inline file size equals the extent sum. External files are
regular tar members whose size equals the pointer-text length.

Effective tar directory names have exactly one trailing `/`; remove it before
comparing with the manifest path. Directory and symlink effective sizes MUST be
zero; neither kind carries a payload. `linkpath` applies only to symlinks.

### Paths

Archive paths are relative UTF-8, compared bytewise without Unicode
normalization. They use `/` separators and contain no NUL bytes, empty
components, `.` or `..` components, leading `/`, or trailing `/`. Manifest
paths are limited to 4096 bytes, with at most 255 bytes per component. A tar
directory name may be one byte longer for its trailing `/`. No root-directory
entry is stored.

Paths MUST be unique. Every ancestor directory MUST have an explicit entry; a
regular file or symlink cannot be an ancestor. Physical member order is
independent of manifest path order.

### Symlinks

Symlink targets are nonempty UTF-8 text without NUL, at most 4096 bytes.
Writers and readers MUST preserve target bytes without normalization or
rewriting. Absolute targets, dangling links, cycles, and targets containing `.`
or `..` components, repeated slashes, or trailing slashes are permitted.
Archive-path component restrictions do not apply to symlink targets.

Lookup returns the entry at the exact archive path without following symlinks.
A read-link operation returns that entry's stored symlink target (`linkname`);
it MUST reject entries of other kinds. File reads MUST reject directory and
symlink entries. Automatic symlink resolution is outside v1.

## Entry-oriented manifest

The [manifest schema](#manifest-schema) defines sequence, entry, extent, and
standalone-reference structures. This section defines encoding and cross-field
rules.

The metadata region encodes a deterministic CBOR sequence (RFC 8742). Every
item uses RFC 8949 core deterministic encoding. Emit exactly one header map,
followed by zero or more entry tuples:

```text
{"version": 1, "required_features": [...], "x-...": ...}
entry
entry
...
```

An empty manifest contains only the header. Entries MUST be strictly sorted by
UTF-8 path bytes across the entire sequence; physical tar order may differ. The
sequence has no enclosing array, entry count, end marker, pages, page
references, or global frame or object tables. Readers derive the entry count
and may build a lookup index while parsing, but MUST NOT use it until the
complete sequence is authenticated and validated.

Each [metadata wrapper](#metadata-region) contains a frame that decodes to a
nonempty sequence segment. Segment boundaries MAY split any item, including its
CBOR header. Readers MUST parse incrementally across segments and reject
malformed or truncated items, a missing or repeated header, enclosing arrays,
scalars in place of entries, and trailing items or bytes that do not form valid
entry tuples.

The footer's decoded length and SHA-256 cover all decoded segments concatenated
in physical order; there are no per-segment hashes. Readers MUST authenticate
and validate the entire sequence before indexed reads. Aggregate metadata and
parser limits are local policy. The segment limit does not bound the sequence
or individual items.

The CDDL `manifest` group describes consecutive sequence items. Schema tools
that require one value may validate a temporary `[manifest]` array; this array
is never encoded on the wire.

Use preferred integer and length widths, definite lengths, and text-keyed maps
whose keys are sorted by deterministic encoded key bytes. Reject duplicate
keys, trailing item bytes, tags, floats, null, indefinite lengths, and
unsupported simple values. Negative integers fit int64; nonnegative integers
fit uint64. Omit optional fields whose values equal their defaults. These
restrictions apply recursively to extension values.

Implementations MUST use bounded or iterative traversal to prevent stack
exhaustion. A local nesting budget of 64 is a suitable default. Each sequence
item starts at depth zero; each array element, map key, or map value increases
depth by one. Exceeding a configured nesting or item budget is a local resource
rejection. The schema and per-segment wire limits still apply.

### Header fields and namespace

The header requires `version` and `required_features`. Version is 1. Only `x-`
extension fields may be added. Entry count is derived from the subsequent
tuples; `entries`, `entry_count`, `index`, and root wrappers are forbidden. See
[Extensions and versions](#extensions-and-versions) for extension rules.

The [lexical grammar](#lexical-grammar) defines `required-feature`. A name is
1..128 ASCII bytes. It starts with a lowercase letter, followed by lowercase
letters, digits, or `.` or `-` paired with a following letter or digit.
Leading, trailing, and adjacent separators are forbidden. The array is bytewise
sorted and unique. Unknown required features are rejected. `external-content`
occurs exactly when any entry uses object sources.

### Entries

Each entry uses this tuple, with no encoded `size` field:

```text
[path, type, mode, uid, gid, mtime_ns, extents, ?attributes]
```

`path` obeys the namespace rules. Each complete CBOR entry tuple, including
attributes, is at most 8 MiB and contains at most 65,536 extents. `type` is 0
for a regular file, 2 for a symlink, or 5 for a directory. `mode` is 0..4095;
`uid` and `gid` are uint64; `mtime_ns` is signed int64 Unix-epoch nanoseconds.
Entries record effective metadata after PAX overrides.

The optional `attributes` map holds extension fields and symlink targets.
`linkname` is required for symlinks and forbidden otherwise; it preserves the
exact effective symlink target. Other attribute names MUST start with `x-`. An
empty attributes map MUST be omitted. Directories, symlinks, and empty files
have empty extents. Empty files remain inline. The logical size of a file is
the checked sum of its extent sizes.

The manifest does not retain header offsets, header-sequence lengths, physical
payload sizes, owner/group display names, prefix splits, or file digests.
Reconstruction generates equivalent tar/PAX metadata with new headers,
checksums, and padding; it need not reproduce the original header bytes. Inline
physical payload size equals logical size. External physical payload size
equals the serialized pointer length.

### Extents

Every extent has this tuple:

```text
[size, source, encoded_size, ?offset]
```

`size` is the number of decoded bytes selected, from 1 byte to 16 MiB. `offset`
is the selection's starting position in the decoded source. It defaults to
zero; explicit zero MUST be omitted. Check `offset + size` for overflow and
require it to be at most 16 MiB. After decoding the source, also require the
sum to be at most its actual decoded length.

`source` is an absolute uint64 encoded archive offset or text `sha256:`
followed by exactly 64 lowercase hexadecimal digits. Archive offsets refer to
data frames in this archive only. External addresses identify complete raw
decoded objects and contain no URL, credentials, or storage layout.

For archive sources, `encoded_size` is the exact complete encoded frame length,
1..17 MiB. The encoded range, computed with checked arithmetic, MUST end at or
before the metadata region. For external sources it is a positive uint64 hint
for compressed object size. The hint MUST NOT control allocation, truncate
fetching, replace actual-byte limits, or reject an equivalent recompressed
object of a different length.

A file's extents MUST be entirely archive-backed or entirely external. An
external object may hold one file, part of a file, or ranges from several
files; external selections may repeat or overlap. Archive extents select the
file's own physical payload in logical order, as established by full
validation. Multiple members may share a frame, and a member may span frames.

Source validation follows the [frame
requirements](#zstandard-frame-requirements) and [external verification
policy](#external-identity-and-verification). See
[Security](#security-considerations) for integrity guarantees.

### Derived values and coverage

These values are derived, not additional manifest fields:

| Value | Definition |
| --- | --- |
| `logical_size(entry)` | Checked sum of decoded extent `size` values; zero for directories/symlinks. |
| `physical_size(member)` | Effective tar size after PAX overrides: original bytes for an inline file, pointer-text bytes for an external file, zero for other kinds. |
| `effective_header_size(member)` | 512 bytes, or 512-byte local PAX header + its padded payload + the 512-byte member header. |
| `payload_offset(member)` | Decoded member start + effective header size. |
| `member_end(member)` | Payload offset + `roundUp(physical_size, 512)`. |
| `raw_source_size` | Actual complete decoded data-frame/object length, determined by decoding rather than an external encoded-size hint. |

For encoded data-frame sizes `c_i` and decoded sizes `d_i`, the frame starts
satisfy `E_0 = D_0 = 0`, `E_(i+1) = E_i + c_i` and `D_(i+1) = D_i + d_i`. The
final encoded end equals manifest start `T`. The decoded member sequence starts
at zero; every next member starts at the previous `member_end`. Exactly 1024
zero bytes follow the final member (or start at decoded zero for an empty
archive), and their end equals the sum of all `d_i`. There are no undecoded
gaps or trailing physical bytes.

For an inline extent selecting frame `i`, its decoded interval is `[D_i +
offset, D_i + offset + size)`. In logical order, those intervals MUST cover
exactly that member's physical payload, without reordering, overlap, gaps, or
another member's bytes. Full archive validation establishes this mapping.
Selective reads check metadata and fetched-source bounds without establishing
physical membership.

Aggregate logical content is the sum of each regular file's logical size,
including files that reuse objects or decoded bytes. It is neither a stored
field nor a limit on duplicate thin content. Implementations using bounded
integers MUST detect and report counter overflow.

## External references and pointer text

### Standalone content references

A standalone external reference is the deterministic CBOR map `{"version": 1,
"extents": [object_extent, ...]}` using the same extent tuples as entries. It
stores neither a whole-file object ID nor an explicit logical size. A reference
has 1..65,536 object-only extents; empty content remains inline.

### Physical pointer payloads

Pointer payloads follow the [lexical grammar](#lexical-grammar):

```text
version zstar-pointer-v1
chunk sha256:<hash> <size> <encoded_size> [<offset>]
```

There are 1..65,536 chunk lines, in reconstruction order. Pointer text is at
most 16 MiB. Every line ends with LF. Decimal values are positive canonical
spellings (a nonzero digit followed by digits, no leading zeros) and MUST fit
uint64. A zero offset is omitted. Hashes use exactly 64 lowercase hexadecimal
digits. Reject BOM, CR, blank lines, extra whitespace, unknown lines, missing
final LF, and trailing bytes.

Only entries with external extents are automatically resolved. Inline content
remains literal even if it resembles a pointer. Full archive validation parses
pointer text and compares all tuple values with entry extents. Recompression
may make the encoded size hints stale without changing object identity or
reference validity.

### External object resolution

A resolver supplies one complete object of at most 17 MiB encoded and 1..16 MiB
decoded. Decode exactly one independent frame with no dictionary or trailing
bytes, enforce input, output, and window limits, and verify the complete
raw-object SHA-256 under the selected policy before selecting bytes. Each
lookup returns one complete encoded representation, reports a missing object,
or fails with a transport error. A response MUST NOT mix object versions or
encodings. Equivalent representations MAY differ between complete lookups,
including recompression with different encoded lengths, unless an adapter
promises a stronger snapshot. The SHA-256 address remains the object's
identity.

Missing objects, malformed encodings, hash failures, and local resource
rejections are distinct outcomes. Sources and caches follow the [reader
profile](#reader-implementation-profile).

## Validation and selective reads

Metadata readers MUST validate footer structure and bounds, the complete
manifest decoded length and hash, deterministic CBOR, sequence schema, the
complete namespace, global ordering, and required-feature agreement before
using indexed ranges. Selective readers MUST also validate selected source
frames and extent bounds. Implementations MUST reject unsupported versions,
unknown required semantics, malformed data, overflows, and digest mismatches. A
failed Zstar check MUST NOT silently fall back to unverified tar extraction.
Source snapshots, cache provenance, and ownership follow the [reader
profile](#reader-implementation-profile).

A failed required check stops the operation. Source validation follows the
declared external SHA-256 policy.

| Check | Metadata | Selective read | Full archive | External closure |
| --- | --- | --- | --- | --- |
| Footer and complete manifest | All | All | All | All |
| Physical data frames | None | Intersecting sources | All | All |
| Tar headers, payload mapping, pointers, padding and end records | None | Not established | All | All |
| External objects and selection bounds | None | Intersecting sources | None | All referenced selections |

External-closure validation includes full archive validation. Opting out of
external SHA-256 verification still requires object framing and bounds checks,
but the result cannot claim a verified closure.

### File reads and verification scopes

For a file request `(offset, length)`, compute logical size by checked extent
summation. Both request values must fit uint64, with `offset <= logical_size`
and `length <= logical_size - offset`. Reject out-of-range requests rather than
truncating them. A valid zero-length request fetches no content, including at
EOF, but still requires footer and complete-manifest hash validation.

Use cumulative extent sizes to locate only sources intersecting the request.
Decode each complete fetched source under its source-kind rules. Check each
complete declared selection against the actual decoded length, then return the
requested bytes in logical order. A complete-file read does not establish a
whole-file hash.

Selective reads establish consistency with hashed metadata and checked fetched
sources; they leave unread headers, pointer text, padding, and end markers
unvalidated.

### Full archive and external-closure validation

Full archive validation MUST scan every physical data frame and tar member,
validate checksums, effective metadata, inline payload mapping, pointer-text
agreement, zero padding, physical coverage, and exactly two final zero records.
Every manifest entry MUST correspond to exactly one physical tar member, and
every physical tar member MUST correspond to exactly one manifest entry. Reject
missing, unindexed, or duplicate members, including directories, symlinks, and
empty files. A local PAX header belongs to its following member and is not a
separate manifest entry.
External-closure validation additionally resolves all external selections.

### Verification claims

Footer and manifest digest checks and codec checks cannot be disabled.
External-object SHA-256 follows the [verification
policy](#external-identity-and-verification). Digests establish internal
consistency, not authenticity. No v1 wire digest identifies the exact complete
encoded archive.

## Extensions and versions

Footer profile and manifest versions are both exactly 1. Pointer version 1
corresponds to the literal marker `zstar-pointer-v1`. Reject other versions.

Core maps accept extension fields only where the CDDL permits them. Extensions
exist only in the manifest header and entry attributes; standalone content
references accept only their declared fields. Extension names are valid CBOR
text beginning with `x-`, with no suffix restriction. Values obey the CBOR
rules above. Maps within extension values use text keys under their published
schema; those keys need not start with `x-`. Readers MAY ignore optional
extensions; semantics required for correct interpretation MUST be declared in
`required_features`. Unknown unprefixed fields and unknown required feature
names are rejected. Writer extension-preservation requirements are in the
[writer API contract](#writer-api-contract-normative-profile). Extension and
required-feature names SHOULD use collision-resistant namespaces. Incompatible
core semantics require a new version/profile.

## Failure classes

Results distinguish absent or invalid Zstar format, malformed structure,
unsupported core versions, unsupported required semantics, integrity failure,
missing external content, transport failure or unavailable content, invalid logical
requests, and local budget rejection. SDKs choose their exception names.
Violating a wire limit makes input malformed; exceeding a lower local budget
may reject valid input. A hash or checksum mismatch is an integrity failure
when distinguishable from a codec structure error.

Recognition, metadata authentication, and required-feature checks precede
indexed use. Complete source validation precedes returning selected bytes. For
independent defects, an operation may report any applicable failure unless a
dependency requires another check first.

## Writer API contract (normative profile)

A writer API that reads and rewrites entries or manifest-header extensions MUST
preserve their values or explicitly report their loss. Unknown required
semantics remain an error. Implementations choose how their APIs preserve
extensions.

Writers MUST accept arbitrary entry insertion order and preserve
caller-supplied metadata. Tar order MUST follow insertion order. Writers SHOULD
bound memory by spilling finalized entry records to temporary storage. Before
emitting the manifest, writers MUST sort entries by UTF-8 path bytes, reject
duplicates, and validate ancestor directories and required-feature agreement.
Payloads SHOULD stream through bounded data-frame buffers; callers MUST NOT be
required to sort input.

Writers MUST honor explicit storage selections or report a conflict. A portable
writer cannot silently externalize a selected member. Producers may decline
optimization hints with diagnostics, but hints must not silently change the
requested capture scope. Capture and restoration follow the [filesystem
profile](#filesystem-capture-and-restoration-profile).

## Reader implementation profile

This profile defines source snapshots, verification, cache ownership, and
parser and resource budgets. Implementations choose their APIs, cache
placement, eviction policies, and transports.

### Source snapshots

For its lifetime, a reader session MUST bind source length and identity,
footer, authenticated manifest, frame reads, and cached archive bytes to one
immutable snapshot. Source replacement or instability MUST invalidate affected
state or fail the operation. Different snapshots MUST NOT be silently combined,
even when external SHA-256 checks are skipped. Native callers must keep
borrowed archive buffers immutable. Remote adapters may pin an immutable
version or use a strong ETag with conditional reads.

### External identity and verification

External objects are identified by the SHA-256 of their complete decoded bytes.
A reader MAY reuse a verified raw object after equivalent recompression. Cache
identity MUST NOT depend on the compressed size hint. Resolver/store namespaces
MUST be isolated where unverified data from one source could otherwise be
accepted for another. Cached objects must include provenance sufficient to
support the reader's declared verification policy.

External SHA-256 verification is enabled by default. An API MAY expose an
explicit opt-out, which does not disable metadata SHA-256, framing, checksums,
decoded bounds, range bounds, or pointer validation required by the operation.
Bytes loaded without hashing MUST be reported as unchecked. They MUST NOT be
promoted or returned as verified without a successful hash of the complete
decoded object. Failed promotion MUST NOT expose unverified bytes to a verified
caller.

### Cache ownership

Cache capacity includes retained payloads and bookkeeping. Active streams,
caller-owned entries, and returned buffers may retain memory separately; APIs
SHOULD document these costs. Returned borrowed or shared bytes MUST remain
valid after cache eviction. Mutable callbacks MUST NOT alter retained
validation proofs or verified cache bytes.

### Temporary storage and cancellation

Temporary stores and worker queues MUST have explicit budgets. Operations MUST
release owned resources on success, failure, cancellation, or close. Cleanup
must preserve the primary failure and report cleanup failures separately.
Noninterruptible I/O or codec work MUST retain its capacity permit until the
work finishes, even if the requesting future is cancelled. Implementations may
coalesce concurrent cache misses; this optimization MUST preserve cancellation,
resource limits, and verification provenance.

### Manifest parsing and index budgets

Readers MAY impose lower local budgets and MUST distinguish those failures from
malformed input. Nesting, item, aggregate metadata, and index budgets are
implementation policy, not additional wire bounds.

Parsing MUST consume sequence items incrementally, retaining at most an item
and bounded read-ahead in addition to the parsed index. Aggregate decoded-byte
budgets apply before parsing. Disk spooling bounds spool memory; it does not
bound the parsed lookup index. Index memory, temporary parsed values, and codec
workspaces contribute separately to memory use.

## Filesystem capture and restoration profile

Filesystem capture and restoration MUST satisfy this profile and the applicable
reader and writer requirements.

### Capture

Writers MUST capture symlinks as symlink entries by default, preserving their
target text without following the target. Following the target during capture
requires an explicit caller request; the resulting entries describe the
captured files or directories. Symlinks contain neither file payloads nor
external extents.

Capture MUST sort paths by UTF-8 bytes before writing tar members. By default,
it MUST normalize regular file modes to 0644, or 0755 when any source
executable bit is set; directory modes to 0755; and symlink modes to 0777. UID,
GID, and modification time MUST be zero and special bits MUST be cleared.
Capture MUST provide an explicit metadata-preservation option that retains each
entry's own mode, ownership, and nanosecond modification time. Low-level writer
APIs retain caller-supplied metadata. Capture policy does not authorize
extraction metadata operations; restoration authorization remains separate.

### Restoration

#### Symlink preservation

Restoration MUST recreate symlinks with their exact stored target text by
default, including absolute targets, dangling links, cycles, and targets
outside the destination root. It MUST NOT require targets to exist, rewrite
targets, or replace links with target content. A caller MAY explicitly select a
stricter symlink policy; rejection under that policy does not make an otherwise
valid archive malformed. If the destination cannot represent a link or its
target text, restoration MUST report an error rather than silently convert or
omit it.

#### Destination confinement

All destination writes and metadata changes MUST stay within the destination
root. Restoration MUST NOT follow symlinks when creating entries or applying
metadata. This applies to both preexisting and newly restored links, including
during concurrent changes to destination paths. A preserved link may point
outside the root; restoration MUST NOT access that target. Restorers SHOULD
create directories and regular files before symlinks, regardless of physical
member order.

#### Host paths and collisions

Archive `/` separators MUST map to host directory separators. Every other
archive component MUST remain exactly one host component, without separator
reinterpretation, Unicode normalization, reserved-name substitution or lossy
text conversion. A restorer MUST fail and report an unrepresentable entry; this
is a host limitation, not malformed wire data. Collision detection MUST include
host-equivalent identities on case-insensitive or normalizing filesystems.
Restoration MUST reject destination collisions and MUST NOT silently normalize
archive path identities. Ownership and set-id bits MUST NOT be applied without
caller authorization.

### Metadata and completion

For each entry kind, unauthorized or unsupported mode, ownership, timestamp, or
special-bit operations MUST fail the entry or produce a partial result
identifying every omitted field. A restorer MUST NOT claim complete metadata
restoration while silently dropping fields. Link metadata MUST be applied to
the link itself and MUST NOT fall back to modifying the target. Restorers
SHOULD finalize directory metadata after descendants, so creating children does
not alter final timestamps and restrictive modes do not prevent descendant
creation.

A stricter caller policy may reject valid archive paths or symlink targets; the
result MUST identify the policy or host limitation and MUST NOT describe the
archive as malformed.

## Security considerations

Bound decompression, CBOR traversal, allocations, temporary storage and
parallel work before consuming untrusted input. A selected 1-byte range can
require fetching and decoding an entire source. Selective validation leaves
unread physical tar data unvalidated; callers requiring those checks use full
validation. Archive extents carry no frame table, so a selective reader knows
whether bytes at a source offset decode as a valid frame. Full archive
validation is required to establish that the offset is an original frame
boundary.

Metadata SHA-256 and data checksums establish internal consistency, not
publisher authenticity. Replacing both content and metadata can produce a
different, internally consistent archive. Inline data is protected by codec
checksums rather than a cryptographic binding to the manifest. Skipping
external SHA-256 additionally forfeits the binding to raw object addresses;
unchecked bytes MUST NOT be represented as verified.

Archive replacement MUST respect the session snapshot contract. Resolving a
shared object reveals all its decoded bytes, including bytes outside the
selected extent; producers should partition objects by disclosure policy.
Credentials and transport URLs are adapter policy and MUST NOT appear in
content addresses. Untrusted paths and symlink targets require the [filesystem
profile](#filesystem-capture-and-restoration-profile) to prevent target
traversal, out-of-root writes and host-identity collisions.

## Manifest schema

This CDDL defines the CBOR structures. The preceding sections define
deterministic encoding, namespace rules, and cross-field invariants.

```cddl
; Normative entry-oriented v1 structure. See v1.md for deterministic encoding,
; bounded nesting, sorted namespace and required-feature agreement.
; A CBOR sequence group: emit these items consecutively, without an array.
manifest = (manifest-header, * entry)
manifest-header = {
  "version": 1,
  "required_features": [* required-feature],
  * extension-key => extension-value
}

entry = file-entry / directory-entry / symlink-entry
entry-fields = (
  mode: 0..4095,
  uid: uint,
  gid: uint,
  mtime-ns: -9223372036854775808..9223372036854775807
)
file-entry = [
  path: archive-path, type: 0, entry-fields,
  extents: [*65536 archive-extent] / [1*65536 object-extent],
  ? attributes: extension-attributes
]
directory-entry = [
  path: archive-path, type: 5, entry-fields,
  extents: [], ? attributes: extension-attributes
]
symlink-entry = [
  path: archive-path, type: 2, entry-fields,
  extents: [], attributes: symlink-attributes
]
archive-path = tstr .size (1..4096)
archive-extent = [
  size: 1..16777216, source: uint,
  encoded-size: 1..17825792, ? offset: 1..16777215
]
object-extent = [
  size: 1..16777216, source: object-address,
  encoded-size: 1..18446744073709551615, ? offset: 1..16777215
]
object-address = tstr .regexp "sha256:[0-9a-f]{64}"
symlink-attributes = {
  "linkname": tstr .size (1..4096),
  * extension-key => extension-value
}
extension-attributes = { + extension-key => extension-value }
extension-key = tstr .regexp "x-[\\s\\S]*"
extension-value = uint / (-9223372036854775808..-1) / bool / tstr / bstr
                / [* extension-value]
                / { * tstr => extension-value }

required-feature = (tstr .size (1..128)) .regexp "[a-z]([a-z0-9]|[.-][a-z0-9])*"

content-reference = { "version": 1, "extents": [1*65536 object-extent] }
```

## Lexical grammar

This ABNF defines complete pointer payloads, required-feature names, and PAX
decimal fields. The preceding sections define numeric and size bounds.

```abnf
; Normative RFC 5234 / RFC 7405 grammar. Input is consumed in its entirety.
; Numeric value bounds and decoded/encoded size rules are defined in v1.md.
; SP, LF and DIGIT are RFC 5234 core rules.
pointer = version-line 1*65536chunk-line
version-line = %s"version zstar-pointer-v1" LF
chunk-line = %s"chunk" SP object-address SP positive-decimal SP positive-decimal [SP positive-decimal] LF
object-address = %s"sha256:" 64lower-hex
lower-hex = DIGIT / %x61-66
positive-decimal = %x31-39 *19DIGIT

; A complete required-feature is additionally limited to 1..128 ASCII bytes.
required-feature = lower *(alnum / separator alnum)
lower = %x61-7A
alnum = lower / DIGIT
separator = %x2D / %x2E

; PAX decimal fields permit leading zeros; pointers do not.
pax-uint = 1*DIGIT
pax-mtime = [%s"-"] 1*DIGIT [%s"." 1*DIGIT]
```
