# Rust S3 adapter

`zstar::s3` is available with the `s3` feature, which also enables `http`.
It uses the maintained `object_store` S3 client for signing, pooled
connections, credentials, retries, and native multipart uploads. Configure an
`AmazonS3Builder`, build an `Arc<AmazonS3>`, and reuse it across readers and writers.
The builder supports AWS credentials and S3-compatible endpoints, including
[RustFS](https://github.com/rustfs/rustfs). Storage credentials, endpoints, bucket names, and URLs are never archive
metadata.

## Read an archive

```rust,no_run
use std::{num::NonZeroUsize, sync::Arc};
use zstar::{Archive, ReaderOptions};
use zstar::s3::{AmazonS3Builder, Path, S3BlobStore, S3RangeSource};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let store = Arc::new(
        AmazonS3Builder::from_env()
            .with_bucket_name("my-bucket")
            .build()?,
    );
    let source = Arc::new(S3RangeSource::new(store.clone(), Path::from("data.zstar")));
    let blobs = Arc::new(S3BlobStore::new(
        store,
        Path::from("objects"),
        NonZeroUsize::new(8).unwrap(),
    ));
    let archive = Archive::open_with_options(
        source,
        ReaderOptions {
            resolver: Some(blobs),
            ..Default::default()
        },
    )
    .await?;
    let bytes = archive.read_range("large.bin", 0..4096).await?;
    println!("Read {} bytes", bytes.len());
    Ok(())
}
```

`S3RangeSource` pins the first observed size and ETag/version, sends conditional
range requests, and rejects mismatched or oversized responses. Its default
maximum range is 64 MiB; override with `with_max_range_bytes`.

`S3BlobStore` reads/writes complete independent Zstandard objects of at most
16 MiB raw and 17 MiB encoded. SHA-256 names raw bytes. The default key is
`<prefix>/<lowercase hex digest>.zst`; `with_key_mapper` supports other layouts.
`put` hashes first and skips the encode and upload when an object already
exists under the content-addressed key (one HEAD); the returned extent then
reports the stored object's size. New uploads use conditional creation, preserving
objects written concurrently and reporting their stored size. Existing empty or
oversized objects are rejected. Readers still verify the SHA-256, so a
damaged or foreign object under a key fails loudly at read time rather than at
write time. Recipes can select whole files, file pieces, or slices of objects shared by
multiple files. `put(Bytes)` returns a complete `Extent` with its decoded size,
SHA-256 source and actual encoded-size hint. `get_encoded` fetches bounded encoded
bytes in one GET without a decoded adapter cache. Readers own decoding, SHA-256 verification,
cache validation, and concurrent shared reads. Object I/O and upload codec jobs
have a shared concurrency bound. Backend errors retain the error category while
redacting details that might contain signed URLs.

For presigned GET/PUT, pass `S3RequestProvider` to
`zstar::http::HttpRangeSource::with_provider`. It uses the configured credential
provider to sign requests as needed, including on expiry/authentication refresh.
GET size discovery uses GET rather than HEAD.

## Manifest discovery metadata

Completed archive uploads can attach `zstar-version`, `zstar-manifest-position`
(`offset:encoded_size`) and `zstar-manifest-sha256` (decoded manifest SHA-256).
`put_archive(store, path, encoded_bytes)` inspects only the footer and uploads the
completed buffer with all three user metadata keys. `archive_attributes(footer,
object_size)` provides the same attributes for caller-managed `PutOptions` or
`BufWriter::with_attributes`. Both validate footer coverage; they do not certify
unread archive contents.

`S3RangeSource` obtains these hints from its pinned HEAD. The reader can fetch a
manifest and its footer in one GET when the complete tail is at most 1 MiB and
within the encoded metadata budget. Missing/invalid/stale/large hints use standard
footer discovery. The actual footer remains authoritative for decoded size and
digest; metadata SHA-256 is informational. See the
[key definitions](#discovery-key-definitions) below for exact keys and byte ranges.

## Discovery key definitions

This informative convention allows S3 user metadata to duplicate archive
discovery information without changing the archive format. SDK upload helpers
write these three keys:

| Key | Value |
| --- | --- |
| `zstar-manifest-position` | Decimal `<offset>:<encoded_size>` |
| `zstar-manifest-sha256` | Lowercase hexadecimal SHA-256 of the decoded manifest sequence |
| `zstar-version` | `1` |

The offset begins at the first manifest segment header. Encoded size includes
all manifest segment headers and payloads and excludes the footer. SDK
metadata maps use the names above; S3 HTTP headers add `x-amz-meta-`. Decoded
size remains in the footer and is not duplicated in user metadata.

Only the position key is needed for the optional opening shortcut. Readers
bind hints to the same pinned HEAD snapshot used for object size and identity.
A bounded combined GET may fetch the entire manifest region and terminal
footer. Its parsed footer must agree with the hinted location before
prefetched manifest bytes are used. The actual footer, manifest digest,
decoded-size budgets and namespace validation remain authoritative. The
checksum annotation is informational; it does not authenticate metadata
independently. Missing, malformed, unknown-version, stale or oversized hints
fall back to standard footer discovery. Transport or snapshot failures remain
errors rather than reasons to weaken conditions.

## Write an archive

`BufWriter` is re-exported from `object_store` and implements Tokio `AsyncWrite`.
Use `with_capacity` (at least 5 MiB for S3) and `with_max_concurrency` to bound
multipart buffers and parallel parts. Streaming writers may omit discovery
metadata because the final offset becomes known after multipart initiation;
attach attributes before writing only when the footer is already known.
`Builder::finish` flushes archive bytes;
`shutdown().await` completes the upload. Borrow the sink so it remains available
for `abort().await` after an encoding or upload error:

```rust,no_run
use std::sync::Arc;
use tokio::io::AsyncWriteExt;
use zstar::{Builder, Result};
use zstar::s3::{AmazonS3, BufWriter, Path};

async fn upload_archive(store: Arc<AmazonS3>, path: Path) -> Result<()> {
    let mut upload = BufWriter::new(store, path);
    let result: Result<()> = async {
        let mut builder = Builder::new(&mut upload);
        builder.append_bytes("hello.txt", b"hello").await?;
        builder.finish().await?;
        upload.shutdown().await?;
        Ok(())
    }
    .await;

    if result.is_err() {
        // Preserve the original error if cleanup also fails.
        let _ = upload.abort().await;
    }
    result
}
```

Dropping a writer alone does not guarantee remote multipart cleanup. Configure a
bucket lifecycle rule for abandoned uploads. Presigned multipart orchestration
is not yet implemented.

## Disposable integration test

The integration test accepts only a local endpoint:

```sh
nix develop --command just check-integration
```

The test creates a unique bucket, exchanges real inline/external archives through
native S3 and presigned GET/PUT, checks exact symlink text, completes an 11 MiB
multipart upload, and aborts another upload. Unit tests use an in-memory store to
check replacement detection, concurrent creation, cancellation bounds, stale
size hints, malformed responses, and reader-owned verification/cache behavior.
